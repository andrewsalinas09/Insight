# MCP instructions

The text `insight mcp` gives an agent up front (MCP `instructions`). Everything after the first `---` line is served verbatim; it's compiled into `insight.exe` from this file (`crates/insight-mcp`). It was adapted from the Round 4 runtime-Claude simulation and finalized at M2 to describe only what's built. Add a line when a tool lands (`compare`, `tag_coverage`, `reach()`/`nid()`, the `writers` and `race_candidates` views, pedantic switches). The ADRs, BUILD-QUESTIONS and SCHEMA.md win over this text.

---

Insight is a read-only, deterministic graph of a project's code at a snapshot. Its facts are exact but incomplete, and every gap is stated. Deciding what they mean is your job. Insight has no framework or library knowledge: everything is in generic programming concepts (containers, calls, value flow, literals, names).

1. **Call `status` first.** It lists projects and their snapshots, what's loaded, the live schema, enum values with counts, the exact definition of each `follow` token, the shipped views, the frozen-source folder, the ceilings, and what's not built yet.
2. **Load** with `load(project)`. It becomes the unqualified `main` schema and stays pinned until you `load` again without an alias. `load(project, alias=…)` attaches another snapshot for SQL as `<alias>.<table>`. `build` makes a new snapshot of an approved project. It never switches what's loaded, and nothing over MCP can create or approve a project: that's the user's step.
3. **Find things** with `sql`: one read-only SQLite statement. You choose `max_rows` and `timeout_ms` within the ceilings, and the result always reports the total row count. Node ids are paths (`app/src/App.tsx › MainApp › graftNode`); `nodes.path LIKE '%› name'` finds by name. For text search, Grep and Read the frozen-source folder (exactly the snapshot's bytes), not the working tree.
4. **Trace** with `path(from?, to?, follow=[…])`. Nothing is followed unless you name it: `call`, `handoff`, `literal`, `names`, and for data `data` (assign, result, return, argument→parameter), `write`, `access`, `read`. Data reaching a function arrives at its parameter; end a data route at a parameter, a state or an external leaf. Give both ends for routes between them, only `from` for everything reachable, or only `to` for everything that reaches it. Ends can be lists. Results are labeled hops with receipts. `possible` candidates, cycles and recursion are reported, never hidden. Use `max_occurrences` to skip common strings and `max_depth` to bound route length; pick them per question.
5. **Equality links are shortcuts to review.** `literal`, `names` and `same` (identical source in another repo) are exact equality, not compiler facts: `path` lists them under "to review". Whether one is a real connection (an RPC name, a message type, the same header on both ends of a link) is your call; confirm it by reading both ends.
6. **Setup is your job too.** If a project doesn't build, `status` shows its settings file and the last build log per repo. Diagnose the problem, then propose the fix to the user: toolchain paths, install steps, or check commands in the project's INSIGHT.md. The user approves command changes with `insight approve`.
7. **Unresolved is a fact, not an error.** `resolution='unresolved'` edges and `to_nid IS NULL` mark calls the compiler couldn't pin down. Say so; don't guess.
8. **Read before explaining.** Use `source(refs=[…])` (node ids, `file`, `file:line`, `file:start-end`; batched; prefix `<schema>:` for an attached repo, as `path` prints them) or the frozen-source folders (one per loaded repo; `status` lists them). Read a function in full before you explain it.
9. **Show while you explain.** `show(view)` puts a view on the user's Insight window (it opens on your first tool call). The user reads your answer in the terminal and looks at the window, so show the code you're talking about.
   - Contents: `open` (boxes to open), `highlight`, `focus` (the camera fits it), `notes` (text, optionally `on` a node), `title`. Anything that refers to code must resolve: a node id, a path suffix (as `path` takes), or `{"path": {from, to, follow, …}}`, which stands for that route.
   - Walkthroughs: `steps`, each with a `focus`, `highlight`, `open` and a `note`. The user steps with Next/Back. `play: true` auto-advances. `show(step=N)` jumps to a step.
   - Condense: `nodes` (draw only these, in their real boxes), `groups` (your own named boxes over real code, nestable) and `collapse` (fold a group or box). Every box that lost children says "+N hidden", and the user can open it. On anything bigger than a small project, an overview should be condensed: the full map buries it.
   - Detours: when the user asks something in the middle of a walkthrough, answer with `aside: true`. They return to the walkthrough, at the step they were on, with one click.
   - Cite as you write: in any note, `[label](ref)` with ref a code reference, `file:line` / `file:start-end`, or `:line` / `:start-end` (lines of what the note is about: its `on`, else the step's trace or focus). The user hovers a citation to see it light up and clicks to go there. Cite every function, field and line number you mention; each must resolve.
   - Trace: the last entry of `stack` can also be a field, static or type: the data trace shows its declaration, the functions that write it and those that read it.
   - Trace: `trace: {stack, line}` opens the trace view, which works like a debugger: one function's code, its callers on the left, and what it calls, reads and writes on the right, in the order written. `stack` is the call stack, outermost first (a `path` search stands for one route), and `line` is the call to start at. A step can carry its own `trace`, so you can walk a call path with a note on each step. The order shown is the order the code is written in. Branches and loops are not evaluated, so say which branch a call is in when it matters.
   - Layout is yours to steer. `layout.chain` lists sequences that are laid out left to right in one row, such as the route you're explaining. `layout.order` puts boxes first within their parent box. `layout.options` passes ELK layered options (e.g. `elk.spacing.nodeNode`, `elk.layered.nodePlacement.strategy`).
   - `selection` says what the user has selected and which step they're on. Read it when they say "this" or "here".
   - Not built yet: groups, collapse, code excerpts, abstraction nodes, example data, and views over attached repos.
10. **Wishes:** if you wish Insight could do something it can't, tell the user why. If they agree, append it to the Wishes section of the global INSIGHT.md. Don't work around a missing tool by guessing.
